## Key research findings (2026-09-29)
- **Alpha 5.0 is real, separate upstream**: lives only at `alpha.ff4fe.com` (no public GitHub repo/branch). Galeswift's own `version.py` comment confirms: "keep MAJOR = 4, to distinguish from main branch v5.0".
- **The old `Tracker V5` folder's `flags_v5.js` is legitimate, not fabricated** — a first research pass concluded it was fake, but diffing it directly against the live `https://alpha.ff4fe.com/script/uispec.js` (the generator's actual client-side flag spec) showed **12,595 of 12,673 flag strings match exactly** (`OA1:char_cecil`, `OA1:collect_boss34`, `OAdo_all:cecil`, `Omode_dkmatter:quests`, `Kstart:hook`, etc. are all real). It's just stale (captured from an earlier a.1/a.2 build vs. live a.3) — reusable ground truth for future flag-string work, not a rewrite.
- **ROM metadata JSON shape genuinely changes under v5.** Both v4.x/Galeswift and v5 embed a JSON blob at ROM offset `0x1FF000` (4-byte LE length) + `0x1FF004` (payload) — unchanged read mechanism, already implemented in `rom-metadata.js`. But `objectives`:
  - v4.x/Galeswift: flat array of pre-rendered description strings (e.g. `"Defeat 20 bosses"`) — what `objectives.js` already parses.
  - v5: nested `ObjectiveGroup[]`: `{ key, name, tasks: [...], rewards: [...] }`, where a task is a plain objective id string, `{objective, threshold}`, or a cross-group reference `{group, req}` (req is a number or `"all"`). Rewards are `{req, description, reward?}`.
  - This shape and the objective-id → display-name dictionary were **ported directly from `Antidale/FeTracker.Common`** (an actively-maintained real FF4FE Alpha 5.0 tracker), specifically `FeTracker.Sni/Models/*.cs`, `Converters/V5ObjectiveConverter.cs`, `Classes/ObjectiveDictionary.cs`, and verified against that repo's own unit test fixtures (not guessed).
- **A real Alpha 5.0 seed ROM was dropped into this folder** (`FF4FE.*.sfc`, seed `3CTM7CN4RE`, `v5.0.0-a.3`) and its embedded metadata was read directly from the file (no hardware needed) to confirm the real JSON shape byte-for-byte matches what was ported from Antidale's fixtures. Its actual `objectives` payload:
  ```
  Group A (objectives_a): quest_tradepan, quest_kaipoinn, quest_traderat, quest_giant, quest_monsterqueen
  Group B (objectives_b): {group: objectives_a, req: 4}, quest_forge  -> reward: "all" = Crystal
  ```
- **RAM addresses (key items, `Objectives__Progress` at $7E1520+i) are unchanged 4.x→5.0** per research — but nobody (including Antidale's own tracker, which flags this explicitly) has confirmed how the per-task progress byte indexes under *nested* v5 groups. This remains the one open, genuinely unverifiable-without-hardware question.

## What's implemented so far
- **`scripts/objectives-v5.js`** (new file): version-gated v5 objective parsing.
  - `isAlpha5Version(version)` — true for `v5.x`/`5.x` version strings (v4.x/Galeswift versions like `"4.7.0.Gale"` don't match, so the existing path is untouched).
  - `OBJECTIVE_LOOKUP_V5` — the ported id→display-text dictionary (`char_cecil` → "Find Cecil", `internal_gp` → "GP Count: {0}", etc.).
  - `parseObjectiveGroupsV5()` / `normalizeTaskV5()` / `normalizeRewardV5()` — parse the raw nested JSON into a normalized shape.
  - `buildObjectiveTasksV5()` — flattens groups/tasks into a flat task list. **Cross-group `{group,req}` references are marked `isComputed: true` and excluded from the polled/byte-indexed task list** (they don't have their own WRAM progress byte — they're a derived count over another group's tasks), so they can't misalign polling for the real leaf tasks. `recomputeGroupRefs()` derives their `current`/`isCompleted` from the referenced group's own task completion state.
- **`scripts/tracking_interface.js`**'s `get_objectives_from_metadata()`: branches on `isAlpha5Version(meta.version)`. For v5, only the *polled* (non-computed) tasks go into `module.objectives`/`module.objectiveTargets` (the same flat-array contract v4.x already uses, so all of `tracker.html`'s existing generic rendering/polling code works unchanged for v5 too, no separate UI needed yet). The full structured data (including reward info and computed group-refs) is stashed on `module.objectiveGroupsV5` / `module.objectiveTasksV5` for a future richer UI.
- `tracker.html`/`launcher.html` version strings bumped to "v1.04 Alpha5"; `objectives-v5.js` added as a plain `<script>` (no ES6 modules, no web server needed — unlike the abandoned `Tracker V5` attempt, this still runs from `file://`).

## XP modifier fix (2026-09-30)

User reported the XP multiplier reading low vs in-game (1.03x shown vs 1.3x real; later 1.12x vs 1.8x real). Found three concrete bugs in `updateXPModifier()`/its flag parsing (`scripts/track.js`), all confirmed against the live generator's `uispec.js` and fixed:

1. **`Xobjbonus:N` (Alpha 5.0's shortened name for Galeswift's `Xobjectivebonus:N`) was never recognized** - the parser only matched the old long form, so the objective-completion bonus silently never applied for either of the user's real seeds (`objbonus:20`, `objbonus:10`). Fixed: accept both spellings.
2. **`Xzonkbonus:N` was parsed into `modeflags` but never applied** in the multiplier calculation at all - dead code. Fixed: applied as `+N% per "zonk"` (a key-item-check location that gave neither a key item nor a character), approximated as `(key-item-checks cleared) - (key items in inventory)` - this can overcount by 1 per character found in a key-item slot (a new Alpha 5.0 shuffle option), since the tracker doesn't yet distinguish that case from a true zonk. Noted as an approximation in code comments.
3. **`Xmaxmulti:N` (caps the final multiplier, Alpha-5.0-only, not in Galeswift at all) wasn't parsed or applied anywhere.** Fixed: parsed and applied as a hard cap at the end.

Verified against both real seeds' actual flag strings (passed via the URL `f=` param, same as manually pasting into the launcher - this is a separate code path from the live ROM-metadata objectives system; `SetModes()` never automatically re-parses flags from ROM metadata, so live auto-tracking users still need the flags pasted into the launcher for anything besides objectives/checks/keyitems/bosses). Hand-verified the arithmetic matches the displayed value exactly for both seeds' real flag strings. `romtest.py` regression suite unaffected.

**Ported the zonkbonus fix back to the released `Tracker v1.03`** (2026-09-30): `Xzonkbonus` is a real, pre-existing Galeswift flag (confirmed in the real flagspec) that was *already* dead code in the shipped v1.03/v1.03.1 before Alpha 5.0 work even started - the bug predates this fork. Applied the same fix there (zonkbonus only - no `maxmulti`/`objbonus` short-form, since those are genuinely Alpha-5-only and don't apply to Galeswift). Verified via a synthetic test and the full `romtest.py` suite on v1.03 itself, both clean. Also found and fixed a pre-existing, unrelated bug in the shared `xptest.py` test suite (comparing the tracker's real `"XP:1x"` text format against a stale `"XP x1"` expected string) - all 10 cases were silently "failing" on a pure string-format mismatch despite every computed value being numerically correct; fixed the test's expected strings, now 0 failures on both v1.03 and this folder. Not yet committed to v1.03's git history.

**Important calibration note from Wylem (one of the FE randomizer's main developers), 2026-09-30:** the real game does NOT compute a clean floating-point multiplier at all - it applies each bonus one at a time using integer arithmetic (no floating point on SNES hardware). Alpha 5.0 specifically computes its *displayed* multiplier by applying all the same bonuses sequentially to a starting value of 1000, then reading back the result - which is "susceptible to rounding errors, hence the 1.99x you see sometimes" (i.e. the real game's own displayed multiplier isn't always a clean number either). Follow-up from Wylem: "figuring out the total multiplier isn't straightforward since different bonus types can have different divisors" - confirming this isn't a simple, guessable formula; different bonus types use different internal fixed-point scales. Our `updateXPModifier()` uses exact floating-point multiplication with no per-step rounding, so it will correctly identify *which* bonuses apply and roughly what magnitude, but can show small decimal differences (e.g. computed 1.32x vs real-game 1.31x) purely from this rounding-methodology difference, not a residual bug. Replicating the exact in-game rounding (order of operations, floor/round convention) would need the actual algorithm from source, not just this description - noted as a possible future refinement, not chased further for now given the current fixes already correctly identify the contributing bonuses.

**Not changed / lower confidence, left for later:** `Xbonuses:mul` (combination mode - additive vs multiplicative across bonus percentages) is real (confirmed in `uispec.js`) but not implemented; the current code already chains bonuses multiplicatively by construction, which may or may not match the intended default when `Xbonuses:` is absent - insufficient evidence to safely change the default without risking a regression on the already-shipped v4.x/Galeswift behavior. Also didn't change `Xkicheckbonus`'s use of `itemcount` (key items in inventory) instead of "key-item checks visited" (they diverge when a character lands in a key-item slot) - lower-impact, more invasive to fix safely.

## Moon checks not populating - fixed (2026-09-30)

User reported Moon key-item-check locations never appearing/activating even after obtaining the Darkness Crystal (which should unlock them). Root cause confirmed directly in code (reproduced with a targeted test, not guessed):

- `applyKSummonKMoonFlags()` (`scripts/track.js`) force-sets `BARON_ODIN`/`FEY_ASURA`/`FEY_LEVIATHAN`/`SYLPH_CAVE`/`BAHAMUT` and all 5 `MOON_*` locations to state `3` ("hidden") whenever `Ksummon`/`Kmoon` are absent from the flags.
- But `Ksummon`/`Kmoon` only mean "key items **can** be placed as summon-boss/moon-boss rewards" (confirmed against both the real Galeswift flagspec and the live generator's `uispec.js`) - they say nothing about whether the location is reachable. Most seeds don't set them (it's one placement option among several), so this hit almost every seed.
- `ApplyChecks()` already has its own, correct, more specific gating for these exact locations (underworld access / Darkness Crystal obtained) - but `ActivateKeyItemLocation()` only ever transitions state `0→1`, never out of state `3`. Once `applyKSummonKMoonFlags()` force-hid these locations at seed load, `ApplyChecks()`'s activation logic could never take effect for the rest of the session, no matter what the player did.
- This is a **pre-existing bug, not Alpha-5-specific** - the exact same code exists unchanged in the released `Tracker v1.03`.

**Fix:** `applyKSummonKMoonFlags()` is now a no-op (kept as a stub with an explanatory comment, call sites left alone) - `ApplyChecks()` is the sole authority on these locations' visibility now, which is how it already behaved for every *other* gated location in the file. Verified: a direct reproduction test (obtain Darkness Crystal → check Moon location state) now shows the correct `0 → 1` transition and the DOM element actually becoming visible, where before the fix it stayed stuck at `3` forever. Full regression suite re-run clean: `romtest.py`, `xptest.py`, `kitest.py`, `chartest.py` all 0 failures.

**Ported to the released `Tracker v1.03` as part of the v1.03.2 hotfix** (2026-09-30, https://github.com/durend/Durendx-FF4FE-Tracker/releases/tag/v1.03.2), along with the zonkbonus, opushbtojump and cnogiant fixes below.

## Surface checks showing prematurely - fixed (2026-09-30)

User reported Tower of Zot, Baron Castle, and Magnes Cave all showing as available with no prerequisite key item (Earth Crystal / Baron Key / TwinHarp respectively). Root cause: this seed's flags include `-pushbtojump`, and `ApplyChecks()` treats `modeflags.opushbtojump` as a universal bypass condition (`keyitems[X] === true || modeflags.opushbtojump`) on **12 separate gates** across key-item locations, character locations, town access and trapped-chest locations.

This isn't a sense-inversion bug (i.e. not "should've meant disabled, code reads it as enabled") - `-Pushbtojump` is an **April Fools joke mode** ("Push B to Jump"), and the live generator's own description explicitly says *"this flag does not affect the randomized placement of progression items."* It has nothing to do with skipping any prerequisite at all - the bypass logic appears to be based on a mistaken assumption about what this flag does (possibly confused with some other, real logic-skip glitch flag).

**Fix:** removed `|| modeflags.opushbtojump` from all 12 gate conditions (`ApplyChecks()`, `scripts/track.js`) - the flag is still parsed (`modeflags.opushbtojump`, in case something cosmetic wants it later) but no longer bypasses anything. Verified with a direct test (seed with `-pushbtojump` and no prerequisite key items - Tower of Zot/Baron Castle/Magnes Cave now correctly stay hidden). Full regression suite (`romtest`/`kitest`/`chartest`/`xptest`) clean.

**Also a pre-existing bug in the released `Tracker v1.03`** - identical pattern, 16 occurrences there. Ported as part of the v1.03.2 hotfix.

A *stable* gap across two different progress states (rather than a growing one) suggests one specific bonus component has a slightly different effective rate than we assume, not accumulating rounding drift - but closing it would need the real per-bonus-type integer constants, which aren't public. Not chased further; documented as an acknowledged, likely-permanent precision gap rather than a bug.
